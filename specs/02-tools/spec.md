# MewCode 工具系统(单步) Spec

> 章节:02-tools
> 上一章:产品规格 spec.md(项目根)
> 后续章节:Agent Loop(自动多步循环)、权限系统、TUI 工具调用确认 UI

## 背景

MewCode 当前是一个纯对话型 TUI:用户输入 → LLM 流式返回文本 → 渲染。模型只能「动嘴」,不能读写文件、执行命令、检索代码。要让它从聊天助手升级为可以「动手」的编码 Agent,第一步是建立工具系统(Function Calling 协议),让模型可以请求工具、本地执行、把结果回灌给模型。

当前代码状态:

- `Message` 只有 role + content + metadata,没有承载工具调用/结果的字段
- `LLMClient` 抽象基类的 chat / chat_stream 接口不接受工具列表
- `CustomAdapter` 流式解析只处理 delta.content,不识别 tool_calls
- `ConversationManager` 把消息序列化到 `~/.mewcode/sessions/`,目前不需要存工具调用记录
- 没有任何工具实现或注册中心
- 默认模型 `mimo-v2.5-pro` 走 CustomAdapter 的 OpenAI 兼容协议;同时项目支持 Claude(Anthropic)、OpenAI、Ollama 三家适配器

本章是工具系统的第一步:跑通**单步**协议(模型请求 → 本地执行 → 回灌结果 → 模型给最终文本回复),覆盖 6 个核心工具。多步自动循环(Agent Loop)留到下一章。

## 目标

- 让模型可以在一次会话中请求 6 个核心工具:ReadFile、WriteFile、EditFile、Bash、Glob、Grep
- 同时支持两种主流工具调用协议:OpenAI tool_calls 模式、Anthropic content block 模式
- 工具执行结果回灌后,模型可以基于结果给出最终回复
- 在 TUI 中以精简轨迹展示工具调用过程,让用户看到模型在做什么
- 通过 config.yaml 控制工具的启用/禁用
- 不破坏现有对话功能和已有 session 文件

## 功能需求

### 工具基础设施

- F1: 提供工具抽象,每个工具能向系统宣告自己的名字、用途说明、输入参数 schema、是否只读、是否破坏性、是否并发安全、所属分类
- F2: 提供工具执行结果抽象,能区分成功结果与错误结果,能携带给模型看的文本内容和给 UI 用的元信息(后者不会进入对话上下文)
- F3: 提供工具上下文对象,在工具执行时提供运行环境信息(至少包含工作目录),由系统在启动时锁定为用户启动 MewCode 的目录
- F4: 工具执行过程中产生的可恢复错误(参数无效、文件不存在、命令执行失败等)必须以「错误结果」返回给模型,不允许抛出异常打断流程;只有系统级故障才向上抛。错误结果在传回模型时按当前协议形态正确表达(OpenAI 协议下 tool 消息的 content 包含错误说明,Anthropic 协议下 tool_result 块设置 is_error 为真)
- F5: 提供工具注册中心,集中管理所有工具,支持按名查找、按配置启用/禁用、按 API 协议输出可被模型识别的工具描述列表

### 六个核心工具

- F6: ReadFile 工具——读取指定文件内容,支持绝对路径和相对路径(相对路径基于工作目录解析),返回带行号前缀的内容,支持分段读取大文件,二进制文件读取被拒绝并提示改用其他方式
- F7: WriteFile 工具——把内容完整写入指定路径,父目录不存在时自动创建,文件已存在则覆盖
- F8: EditFile 工具——基于「旧片段必须在文件中唯一匹配」的方式做局部替换,旧片段未找到或匹配多次都返回错误结果,替换成功后返回修改位置附近的预览让模型自行确认
- F9: Bash 工具——以工作目录为根执行 shell 命令,默认 30 秒超时,标准输出与标准错误合并,过长输出按规则截断,非零退出码作为正常结果返回(不是错误),只有超时算错误
- F10: Glob 工具——按 glob 模式查找文件,支持递归匹配,自动排除常见噪音目录(`.git`、`node_modules`、`vendor`、`__pycache__`、`.idea`),结果按修改时间倒序,有上限保护
- F11: Grep 工具——按正则在文件中检索,支持按文件名 glob 过滤、上下文行数,自动跳过二进制文件和噪音目录,结果有上限保护

### 协议接入与对话流程

- F12: LLM 客户端抽象基类提供向适配器传递工具列表的能力,适配器内部根据各自协议(OpenAI tool_calls 或 Anthropic content block)做翻译;调用方不需要关心协议差异
- F13: 流式响应能解析两种协议的工具调用片段并完整聚合成结构化的「工具调用请求」对象交给上层
- F14: 对话消息模型扩展为同时容纳「工具调用请求」「工具执行结果」两种新结构,既能装 OpenAI 协议形态也能装 Anthropic 协议形态,序列化向后兼容
- F15: 模型请求工具调用时,系统按注册中心查找工具并执行,把结果以协议对应的方式追加进对话历史,然后再发一次 LLM 请求拿到最终回复;本章流程到此结束,不做自动循环

### TUI 与配置

- F16: TUI 在工具调用时显示精简轨迹(调用前一行 `→ 工具名(关键参数)`,执行后一行 `✓ 成功` 或 `✗ 错误:简短说明`),不展开完整输入输出
- F17: config.yaml 增加工具开关配置,支持启用全部、只启用只读、显式列出启用的工具名三种方式
- F18: 系统在每次发起 LLM 请求时自动注入一段精简的英文 system 消息,告知模型当前工作目录、操作系统、工具使用的基本原则(如先用 Grep/Glob 定位再 ReadFile,EditFile 的旧片段要带足上下文以保证唯一)

## 非功能需求

- N1: **跨平台**——所有工具在 Windows / macOS / Linux 上都能工作。Bash 工具调用系统默认 shell(Windows 用 cmd 或 powershell,Unix 用 sh),路径分隔符通过标准库统一处理
- N2: **不破坏现有功能**——纯对话(不调用任何工具)的行为和上一版完全一致,流式渲染、token 统计、session 持久化保持不变
- N3: **向后兼容已有 session**——上一版生成的 session YAML 文件仍可加载,加载时新增字段缺失按空处理
- N4: **错误隔离**——任意一个工具执行失败不会让 MewCode 进程崩溃,也不会让 LLM 请求中断;失败信息以工具结果形式喂回模型
- N5: **输出体积可控**——所有工具的返回内容都有上限,Bash 输出超过 10000 字符做截断、Grep 最多 100 个匹配、Glob 最多 200 个文件,避免单次工具调用把 token 上下文打爆
- N6: **路径安全**——所有文件类工具拒绝读写明显的二进制内容;Bash 不做命令白名单(本章先信任本地环境,权限沙箱留给后续章节);符号链接走操作系统默认行为,不额外展开或限制
- N7: **可观测**——工具调用过程在日志中记录(工具名、参数摘要、耗时、是否错误),便于排查问题
- N8: **可测试**——工具实现与文件系统/子进程的耦合通过依赖注入或参数化做隔离,核心分支可在不依赖真实磁盘的前提下被单测覆盖
- N9: **协议透明**——上层(TUI、ConversationManager)不需要感知 OpenAI 协议和 Anthropic 协议的差异,所有翻译收敛在适配器内部
- N10: **配置默认安全**——config.yaml 不显式配置时,默认启用全部 6 个工具
- N11: **语言策略**——所有进入 LLM 上下文的文本(system prompt、工具描述、工具返回给模型的内容、错误信息中给模型看的部分)统一使用英文;仅面向用户的输出(TUI 状态文案、模型最终回复的渲染、给用户提示的错误摘要)使用中文。工具实现内部以英文构造模型可见的所有字符串

## 不做的事

- 不做 Agent Loop:模型一次工具调用 → 执行 → 回灌 → 模型给最终回复,流程到此结束;不让模型连续调多轮工具
- 不做人工确认/审批:即使 Bash 是 destructive 工具,本章也不弹 TUI 确认窗
- 不做权限沙箱:不限制 Bash 能跑什么、不阻止访问哪些目录、不强制工作目录之外的路径不可写
- 不做并发执行:即便 ReadFile/Glob/Grep 标记了 isConcurrencySafe=true,本章串行执行所有工具调用
- 不做工具调用结果的持久化:本章 session YAML 只新增可选字段以兼容,不要求把工具调用历史完整存盘后还能完美回放
- 不为 Claude / OpenAI / Ollama 适配器做端到端联调:本章重点是 CustomAdapter(默认模型 mimo-v2.5-pro)走通,其他三个适配器只补齐协议层代码并通过单测,不强制要求接真实 API 验证
- 不做工具的「热更新」:工具列表在启动时根据 config 一次性注册,运行时不支持添加/删除
- 不做工具调用的撤销/回滚机制:WriteFile / EditFile / Bash 改完就改完,本章不存快照
- 不做远程工具(MCP、HTTP 工具服务器)集成
- 不做工具描述的多语言版本:所有进入 LLM 的文本统一英文(N11),仅面向用户的 TUI 提示用中文

## 验收标准

### 工具基础设施

- AC1: 启动 MewCode 后,工具注册中心至少包含 6 个内置工具(对应 F6-F11),通过名称可逐个查到,每个都返回完整的 name / description / inputSchema / 元信息
- AC2: 任意工具内部抛出可恢复异常时,调用方收到的是「错误结果」对象(isError 为真),进程不崩溃,LLM 对话流程不中断
- AC3: 工具返回的元信息字段不会出现在传给 LLM 的对话上下文中(可通过观察实际发出的请求 payload 验证)
- AC4: 工具上下文对象在启动时锁定为用户启动 MewCode 时所在的目录,后续运行期间所有文件类工具/Glob/Grep/Bash 都以该目录为根

### 六个核心工具(每条都通过运行真实命令观察)

- AC5: 用 ReadFile 读一个已知文本文件,返回内容是带行号前缀的格式;用 offset/limit 读取大文件时只返回指定区段;读不存在的文件、读二进制文件、传非法路径分别返回 isError=true 的不同错误说明
- AC6: 用 WriteFile 写到一个不存在的多层目录路径,父目录被自动创建,文件内容与请求一致;写已有文件时被覆盖
- AC7: 用 EditFile 替换文件中唯一出现的字符串,文件被正确改动且返回值包含修改位置附近的预览;旧片段重复出现时返回错误并指明出现次数;旧片段不存在时返回错误并提示模型记忆可能过期
- AC8: 用 Bash 执行 `echo hello`、`ls`(或 Windows 等价命令)能拿到正常输出与 exit code 0;执行 `false` 这类失败命令拿到非零 exit code 且 isError=false;执行 `sleep 60`(超过默认 30 秒超时)被截断且 isError=true;执行产生超过 10000 字符的输出能看到截断标记且首尾各有保留
- AC9: 用 Glob 在项目内搜 `**/*.py` 能得到结果列表,按修改时间倒序;搜噪音目录里的内容不会出现在结果里;命中超过 200 时被截断
- AC10: 用 Grep 在项目内搜一个已知存在的字符串,返回 `路径:行号: 匹配行` 格式;命中超过 100 时被截断;搜二进制文件不会出现匹配;支持上下文行数和文件名 glob 过滤

### 协议接入

- AC11: 用 CustomAdapter 调用一个支持 tool_calls 的 OpenAI 兼容模型(或本地 mock 端点),传入工具列表后,模型请求工具时能从流式响应里完整聚合出工具调用对象,包含正确的 id、name、解析后的 input JSON
- AC12: 用 ClaudeAdapter 调用 Claude 模型(或 mock)时,流式响应里 content_block_start / input_json_delta / content_block_stop 序列能被聚合成完整工具调用对象
- AC13: tool_calls 流式聚合在 partial_json 拼接失败时返回 isError 的工具调用对象,不让流处理崩溃
- AC14: Message 模型可以装载 OpenAI 形态(assistant 消息含 tool_calls 字段、user 消息含 tool_call_id+content)和 Anthropic 形态(content 是 block 列表),序列化/反序列化双向无信息丢失
- AC15: 加载上一版生成的 session YAML 文件不报错,所有原有字段保留,新增字段在缺失时按空处理

### 单步对话流程

- AC16: 用户提出一个需要查文件的问题(例如「读一下 src/mewcode/config.py」)→ 模型请求 ReadFile → 系统执行 → 结果回灌 → 模型给出基于文件内容的最终中文回复;整个过程在 TUI 中可见,顺序正确
- AC17: 单步流程中,模型第二次回复(基于工具结果)结束后流程停止,不会自动发起第二次工具调用(即便模型在第二次回复里又输出了 tool_use,本章不再触发执行)
- AC18: 工具执行失败的情况下(如读不存在的文件),模型仍能拿到 isError 的工具结果并基于此给出回复(例如告诉用户文件没找到),整个流程不中断

### TUI 与配置

- AC19: TUI 中工具调用展示为精简两行(调用前 `→ 工具名(关键参数)`,执行后 `✓ 成功` 或 `✗ 错误:摘要`),与普通文本消息样式有明显区分
- AC20: config.yaml 中 tools.enabled 设置为只读列表(`[ReadFile, Glob, Grep]`)时,启动后注册中心只有这三个工具,模型也只看得到这三个;设置为空或缺省时启用全部 6 个
- AC21: 每次 LLM 请求实际发出的 system 消息中包含当前工作目录路径、操作系统标识、工具使用的简短英文原则段落

### 编译/测试/语言策略

- AC22: 项目仍可正常启动(`./start.ps1` 进入 TUI 不报错)
- AC23: `python -m pytest tests/ -v` 全部通过;新增测试覆盖每个工具的成功路径与所有错误分支、注册中心的启用/禁用、流式 tool_calls 聚合、Message 序列化兼容
- AC24: 抓取一次实际的 LLM 请求 payload,检查所有进入 messages 数组和 system 字段的字符串均为英文;TUI 中显示给用户的状态/错误文本均为中文
