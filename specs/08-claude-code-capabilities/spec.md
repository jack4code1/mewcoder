# Claude Code 能力覆盖路线 Spec

## 背景

MewCode 已具备终端交互、多模型适配、六个本地编程工具和多轮 Agent Loop，能够完成基础的“模型调用工具—获取结果—继续推理”流程。项目下一阶段的目标是将这些基础能力演进为可扩展、可控且适合真实项目开发的编码 Agent。

本路线以 Claude Code 的核心使用体验为参照，覆盖图片所列能力：工具调用、Agent Loop、MCP、Skill/Slash Command/Hook、深度权限、上下文与跨会话记忆，以及 SubAgent、Git Worktree 和 Agent Teams。现有工具和 Agent Loop 将保留并作为后续能力的底座。

## 目标

- 让用户可以安全地把外部工具、项目规范和自动化流程接入 MewCode。
- 让 Agent 在长任务和多个会话中保持必要的项目上下文，同时可控制上下文和成本。
- 让复杂任务可以拆分、隔离执行、汇总结果，并保持用户对高风险操作的最终控制权。
- 以可独立交付的阶段推进，确保每一阶段都能在不依赖后续阶段的情况下使用和验证。

## 功能需求

- F1: 工具与 Agent 基线
  - 系统保留并统一管理现有 ReadFile、WriteFile、EditFile、Bash、Glob、Grep 工具。
  - Agent 能在单次用户任务内进行多轮推理、工具调用和结果处理，并向界面持续报告执行进度、错误及终止原因。
  - 后续新增的本地工具、外部工具和子 Agent 操作必须使用同一套工具发现、调用记录和权限判定规则。

- F2: MCP 外部工具接入
  - 用户可以配置、启用、禁用和查看外部 MCP 服务。
  - 已启用服务提供的工具可被 Agent 发现和调用，并在界面中显示来源、输入摘要、执行状态和结果摘要。
  - 服务连接失败、工具描述无效、调用超时和返回错误必须可识别，并不得使当前会话崩溃。
  - 外部工具调用必须受与本地工具等效的权限控制和审计记录约束。

- F3: Skill、Slash Command 与 Hook 自动化
  - 用户可以将可复用的项目工作流定义为 Skill，并在对话中显式调用或由系统在满足条件时建议使用。
  - 用户可以通过可扩展的 Slash Command 执行已注册的操作，而不是依赖硬编码命令分支。
  - 用户可以为会话与任务生命周期事件配置 Hook，使其在预定义时机运行检查或自动化操作。
  - Skill、命令和 Hook 的来源、适用范围、输入要求及实际执行结果必须对用户可见。
  - Hook 的失败不得静默忽略；系统必须明确显示失败并按配置决定是否阻止后续步骤。

- F4: 深度权限防御
  - 系统必须按风险区分只读、受控写入、命令执行、外部工具和高风险操作。
  - 文件操作默认限定在用户选定的工作区；超出工作区的访问必须被拒绝或经用户明确批准。
  - 写入和编辑操作在执行前必须可展示变更摘要，适用时展示差异预览。
  - 命令执行、外部工具调用及高风险操作必须在执行前提供可理解的操作摘要和审批选项。
  - 用户可以对单次操作、当前会话或当前项目授予范围明确、可撤销的许可；不得将临时许可隐式扩展到其他项目。
  - 所有会改变文件、执行命令、调用外部服务或改变权限的操作必须生成可查询的审计记录。

- F5: 上下文压缩与跨会话记忆
  - 系统在发送模型请求前应展示或可查询当前上下文的组成与预算使用情况。
  - 当上下文接近可用预算时，系统应按策略保留当前任务必要信息，并压缩或替换较早且低优先级的会话内容。
  - 用户可以保存、查看、更新和删除项目级记忆及用户偏好；记忆在后续相关会话中可被选择性加载。
  - 压缩和记忆加载必须可追溯：用户能够知道哪些信息被纳入当前请求，以及其来源。
  - 系统不得把一个项目的记忆自动提供给另一个项目。

- F6: SubAgent、Git Worktree 与 Agent Teams
  - 用户或主 Agent 可以把复杂任务拆分为边界明确的子任务，并为每个子任务建立可观察的 SubAgent 执行单元。
  - 子任务应继承最小必要的上下文和权限，而不是默认获得主任务的全部访问范围。
  - 对需要隔离文件修改的子任务，系统可以在独立 Git Worktree 中执行，并向用户显示工作树位置、分支/基线及变更摘要。
  - 用户可以创建由多个长期协作角色构成的 Agent Team，分派任务、查看状态、接收汇总结果，并决定是否接纳各项修改。
  - 多 Agent 并发执行必须受资源上限、冲突检测和权限控制约束；发生冲突时不得自动覆盖用户或其他 Agent 的变更。

- F7: 进度与交付管理
  - 本路线每个能力阶段均维护规格、技术方案、任务分解和验收清单。
  - 任务文档必须反映阶段状态、依赖、验证结果和未解决风险，作为用户查看开发进度的主要入口。
  - 完成某阶段后，变更日志必须记录面向开发者的能力变化、兼容性影响及迁移说明。

## 非功能需求

- N1: 安全优先。任何会扩大文件、命令、网络或外部服务访问范围的能力，必须在启用前向用户说明影响并接受权限控制。
- N2: 可观测性。用户应能从终端界面或保存的记录中追踪 Agent、工具、Hook、MCP 和子任务的状态与结果。
- N3: 可恢复性。单个外部服务、Hook、子任务或模型调用失败不得导致应用崩溃；失败信息应可用于继续、重试或停止任务。
- N4: 向后兼容。已有的模型配置、会话数据和基础工具工作流在升级后应继续可用，除非用户主动启用新的受限策略。
- N5: 可测试性。每个新增能力必须具有单元测试和至少一个跨模块的行为验证；涉及隔离与审批的行为必须覆盖拒绝路径。
- N6: 渐进交付。按“权限基础 → 上下文与记忆 → 扩展机制 → MCP → 隔离并行 → 团队协作”推进；后一阶段不得绕过前一阶段建立的安全边界。

## 不做的事

- 不复制 Claude Code 的品牌、私有服务、云端账户体系或未公开实现。
- 不在本路线内开发 IDE 插件、移动端、代码托管平台或企业级身份管理。
- 不提供绕过用户审批的隐蔽自动执行模式。
- 不将外部 MCP 服务、Skill 或 Hook 视为天然可信来源。
- 不承诺所有模型提供商都支持完全相同的工具调用、并发或上下文能力；差异应明确呈现。

## 验收标准

- AC1: 用户可在同一任务中观察现有工具和 Agent Loop 的多轮执行过程，并能中止运行而不损坏会话。
- AC2: 用户可配置一个 MCP 服务、启用其工具并在对话中看到一次成功或失败的受控调用记录。
- AC3: 用户可注册并运行一个 Skill、一个 Slash Command 和一个 Hook，且能查看三者的执行来源、状态和结果。
- AC4: 对工作区外文件访问、文件写入、命令执行和高风险外部工具调用，系统均会执行已配置的拒绝或审批策略，并留下审计记录。
- AC5: 在长对话中，系统能显示上下文预算并在接近上限时压缩历史；新会话可按项目范围加载用户确认的记忆，且不会加载其他项目记忆。
- AC6: 用户可执行至少两个隔离的子任务，查看各自状态和变更；发生文件冲突或权限不足时，系统不会自动覆盖变更并会报告原因。
- AC7: 用户可创建一个至少包含两个角色的 Agent Team，完成任务分派、状态汇总和结果接纳或拒绝流程。
- AC8: 每个阶段均存在已审批的 spec、plan、task、checklist 文档；任务文档记录实际进度，完成后 CHANGELOG 反映交付内容。
